# Design: Capacity Planning — Resource Scheduling

## Summary

Planix's resource layer provides visibility into person-level capacity, skill availability, and forecast accuracy. Each person has a resource profile (FTE, hours/week, start/end date) and a skill inventory (competencies with proficiency levels). Each week, available capacity is calculated from the profile minus planned absence and overhead. Forecast allocations per task/sprint/project are compared against weekly capacity to surface over/under-booking. Absence-conflict detection alerts when vacation overlaps with forecasted work. Post-project actual hours enable forecast-accuracy retrospectives per skill category. A 12-week heatmap visualizes utilization across the team. Skill matching ranks candidates by match score, available capacity, and cost. What-if scenarios allow planners to explore "what if we take this new project" without mutating live data. Privacy controls ensure sensitive data (salary) is only visible to authorized roles.

## Motivation

Resource allocation is today invisible in Planix — tasks are assigned to people without checking whether they have capacity or the right skills. This leads to overallocation surprises, skill mismatches, and deadline blowups. The resource layer makes allocation decisions informed by real capacity, skill, and historical accuracy data.

## Approach

- **Data**: 7 OpenRegister schemas per the context-brief data model
- **Capacity calculation**: Synchronous on profile/absence mutation; async (nightly) for aging (changing week dates)
- **Alerts**: Async alert-generation job (event-driven + nightly) creates/updates AlertSignal objects
- **Frontend**: Capacity section with list, heatmap, detail, absence manager, and forecast review pages
- **Skill matching**: Algorithm in candidate-picker dialog ranks by (1) match score, (2) available capacity, (3) cost
- **Scenarios**: Mode toggle that clones forecast state locally; "apply scenario" commits changes back to live
- **Privacy**: Field-level RBAC on cost_per_hour; capacity % hidden unless resource-manager role
- **Integrations**: openconnector imports FTE/absence; financeq/purchaseq optional future integrations

## Data Model

### Schemas (OpenRegister objects)

| Schema | Properties | Notes |
|--------|-----------|-------|
| **ResourceProfiel** | persoon (user UID), fte (0.0-1.0), uren_per_week_nominaal (int), kosten_per_uur (float), locatie (string), beschikbaar_van (date), beschikbaar_tot (date, nullable) | One per employee; immutable except dates and FTE. |
| **Skill** | code (slug), naam (string), categorie (enum: taal/framework/domein/soft-skill) | Global skill library; curated by admin or synced from docudesk. |
| **PersoonSkill** | persoon (UID), skill (slug), niveau (enum: junior/medior/senior/expert), zelfverklaard_of_geverifieerd (bool), laatste_evidence_ref (string, nullable) | Junction; many per person. Evidence = docudesk certificate or manager verification. |
| **Afwezigheid** | persoon (UID), type (enum: vakantie/ziekte/opleiding/overig), van (date), tot (date), uren (float, optional override), status (enum: gepland/geboekt/actueel) | Planned = approved leave; geboekt = HR-imported; actueel = finalized hours. |
| **CapaciteitWeek** | persoon (UID), week (ISO week YYYY-Www), bruto_uren (float), afgetrokken_uren_afwezigheid (float), afgetrokken_uren_overhead (float), netto_beschikbaar_uren (float) | Calculated weekly; immutable (recalc on change). Cache per person for 12-week horizon. |
| **ForecastAllocatie** | persoon (UID), project_or_task (uuid, register+schema+objectId), week (ISO Www), gepland_uren (float), skill_vereiste (JSON {skill: niveau, ...}), status (enum: concept/bevestigd) | Mutable; used for "what-if" scenarios. |
| **WerkelijkUur** | persoon (UID), project_or_task (uuid, register+schema+objectId), datum (date), uren (float), omschrijving (string, optional), geboekt_op (timestamp) | Immutable audit log; one entry per day per person per project. |
| **AlertSignaal** | type (enum: overbezetting/onderbezetting/skill-mismatch/afwezigheid-conflict), persoon (UID), periode (week YYYY-Www), ernst (enum: laag/medium/hoog), bericht (string), status (enum: open/erkend/opgelost) | Generated by alert job; status updated manually or by escalation rule. |

### Relationships

- ResourceProfiel → Nextcloud user (external, not stored)
- PersoonSkill → Skill (register:skill, objectId)
- Afwezigheid → ResourceProfiel (no explicit link; join on persoon UID)
- CapaciteitWeek → ResourceProfiel (derived weekly from profile + afwezigheid)
- ForecastAllocatie → Task/Project (register+schema+objectId), ResourceProfiel (persoon UID)
- WerkelijkUur → Task/Project (register+schema+objectId), ResourceProfiel (persoon UID)
- AlertSignaal → ResourceProfiel (persoon UID), CapaciteitWeek (periode week)

## Reuse Analysis

- **ObjectService** — CRUD for all 7 resource schemas; IndexService for list views
- **CnDataTable** — list view for resources, absence, alerts
- **CnDetailPage + CnObjectSidebar** — resource detail, absence detail, alert detail
- **CnFormDialog** — create/edit resource profile, skill assignment, absence, forecast
- **useObjectStore** — pinia stores for resource/skill/absence/forecast/alert/capacity state
- **useListView/useDetailView** — state management for pages
- **PropertyRbacHandler** — field-level access control on cost_per_hour
- **AuthorizationService** — role check for resource-manager vs. team-lead vs. self
- **CnChartWidget** — heatmap visualization (custom ApexCharts integration)
- **WebhookService** — notify when alert status changes (optional)
- **ScheduledWorkflowController** — nightly capacity recalc + alert generation
- **ImportService** — optional HR system import wizard (via openconnector adapters)

No new utilities, stores, or components needed — all platform-provided.

## Frontend Views

### Capacity → Resource List
- CnDataTable with columns: Naam, Locatie, FTE, Nominaal u/wk, Deze week netto (u), Bezetting %, Status
- Sortable by name, FTE, utilization %
- Filters: Locatie, Status (active/inactive), Bezetting range (0-50%, 50-90%, 90-110%, >110%)
- Detail row click → Resource Detail page

### Capacity → Heatmap (12-week horizon)
- Y-axis: list of resource names (sortable, filterable)
- X-axis: ISO weeks W21 → W33
- Cells: color-coded by utilization % (green, yellow, orange, red)
- Hover → tooltip with absolute hours (gepland vs. beschikbaar)
- Click cell → see breakdown of ForecastAllocaties for that person-week

### Capacity → Resource Detail
- Using CnDetailPage + CnObjectSidebar
- Card 1: ResourceProfiel (fte, uren/week, locatie, start/end dates)
- Card 2: Skills (PersoonSkill list with nivaux)
- Sidebar tabs:
  - Absence (Afwezigheid list, inline edit/delete, import button)
  - Forecast (ForecastAllocatie list for next 12 weeks, grouped by week)
  - Actuals (WerkelijkUur table by date, group by project)
  - Alerts (AlertSignaal list, status-update buttons)

### Capacity → Forecast Review (retrospective)
- Date range picker (e.g., past quarter)
- Columns: Person, Forecast (sum hours), Actual (sum hours), Ratio (actual/forecast), Variance %
- Group by skill category (optional) to identify systematic over/under-estimation
- Export as CSV for finance

## Backend Workflow

### Capacity Recalculation (sync on mutation)

1. Resource profile updated (FTE, uren_per_week_nominaal, etc.)
2. Trigger: `ConfigurationService.updateObject(register, schema, objectId, data)`
3. Action: Compute CapaciteitWeek for all weeks in [today, today + 12 weeks] for that person
4. Formula: netto = bruto − sum(afwezigheid.uren) − (bruto × overhead_rate)
5. Upsert CapaciteitWeek objects via ObjectService.saveObject()

### Alert Generation (async; event-driven + nightly)

1. Trigger: After ForecastAllocatie saved or Afwezigheid changed (webhook) + nightly cron job
2. For each (person, week):
   - Fetch CapaciteitWeek for that week
   - Sum ForecastAllocatie.gepland_uren for that week
   - Compare: gepland vs. netto_beschikbaar
   - If gepland > netto_beschikbaar × 1.1: create/update AlertSignaal type=overbezetting with ernst=medium (10-20% overage) or hoog (>20%)
   - If netto_beschikbaar > gepland + 20% and open tasks in backlog exist: create AlertSignaal type=onderbezetting
3. Absence-conflict check:
   - For each Afwezigheid, find ForecastAllocaties that overlap
   - If overlap and no "conflict-acknowledged" flag: create AlertSignaal type=afwezigheid-conflict
4. Skill-mismatch check:
   - For each ForecastAllocatie, check PersoonSkill.niveau matches skill_vereiste
   - If no match or below required level: create AlertSignaal type=skill-mismatch
5. Upsert AlertSignaal objects via ObjectService.saveObject()

### Actual Hours Booking

1. User (or integration) creates WerkelijkUur object via ForecastReview UI or API
2. Immutable audit log entry
3. Aggregate for forecast-vs-actual report

## Privacy & Access Control

- **ResourceProfiel.kosten_per_uur** — visible only to roles: resource-manager, finance-admin, or the person themselves (field-level RBAC via OpenRegister PropertyRbacHandler)
- **CapaciteitWeek.netto_beschikbaar_uren** — visible to resource-manager; others see only "beschikbaar/beperkt/vol" (computed client-side from % utilization)
- **Capacity heatmap** — resource-manager sees % utilization per person; others see only their own row (filtered by useListView)
- **AlertSignaal** — resource-manager sees all; others see only alerts related to themselves

## Integration Points

- **openconnector** — adapters for HR systems (AFAS, Visma, SuccessFactors) import FTE/absence data periodically into Afwezigheid/ResourceProfiel
- **financeq** (future) — kosten_per_uur rolled up for project margin and client billing
- **purchaseq** (future) — external contractors (ZZP) onboarded as ResourceProfiel with external=true flag
- **docudesk** (future) — PersoonSkill.laatste_evidence_ref links to skill certificate storage

## Performance Considerations

- Heatmap queries indexed on (persoon, week); cache 12-week horizon in browser (refresh on mutation)
- AlertSignal table pruned nightly (keep open alerts + last 90 days of closed)
- CapaciteitWeek immutable; future weeks pre-computed on first access (lazy load)
- ForecastAllocatie list paginated (50 per page)
- Skill matching algorithm runs client-side (candidate picker); no expensive server-side ranking

## Open Questions

- Should forecast-vs-actual use actual booking by end user, or HR system punch-card import? (MVP: end-user booking in ForecastReview UI; HR import future)
- Overhead rate: global setting or per-person? (MVP: global admin setting, e.g., 10% for meetings/mail)
- Scenario versioning: keep history of scenarios, or discard on apply? (MVP: discard on apply; history tracking future)
